# Root cause and fix — orphaned PCC rules in the free5gc PCF (issues #1181, #1184, #1185)

## Scope of this bundle

This bundle documents three free5gc issues against the PCF's Npcf_PolicyAuthorization service and the fix we built for them. It contains the three issue descriptions ([issue-1181.md](issue-1181.md), [issue-1184.md](issue-1184.md), [issue-1185.md](issue-1185.md)), a minimal exploit script ([pcf_pcc_rule_leak_exploit.py](pcf_pcc_rule_leak_exploit.py)), a [deployments/](deployments/) folder with the compose files, per-NF configuration and certificates needed to run the stack (stock `docker-compose.yaml`; fixed `docker-compose-fixed.yaml`, which also serves as the image-only overlay for swapping the PCF inside an already-running stock stack), and this report. All three issues have one root cause, so this report describes the root cause once and then the fix that closes all of them together. The affected software is the standalone `github.com/free5gc/pcf` repository at tag v1.4.6 (commit `eb57557`), which is the same revision the stock `free5gc/pcf:v4.3.0` container image is built from; line numbers in this report refer to that revision, while the issue documents quote the v1.4.3 (`df6c0da`) numbers they were originally written against. The defect is classified as CWE-459 (incomplete cleanup) with CWE-770 (allocation of resources without limits) as the exposure it creates.

## Background

When an Application Function authorizes a media session, it sends `POST /npcf-policyauthorization/v1/app-sessions` (create) or `PATCH` on an existing app session (modify). For each media component the PCF builds PCC rules and installs them into the SM policy decision of the UE's PDU session, `smPolicy.PolicyDecision.PccRules`. That decision is persistent state: it lives in `ue.SmPolicyData[smPolicyID]` until the PDU session — and with it the SM policy — is deleted, and it is what the PCF sends toward the SMF on the next successful update. Ownership is the counterpart of installation: a PCC rule is releasable only through the Application Session that references it. `HandleDeleteAppSessionContext` (`internal/sbi/processor/policyauthorization.go:450`) walks `appSession.RelatedPccRuleIds` (`:483`) and calls `(*UeSmPolicyData).RemovePccRule` (`internal/context/ue.go:179`) for each id, which removes the rule together with its associated QoS, traffic-control, charging and usage-monitoring entries and prunes stale references from all other app sessions.

## Root cause

The two handlers install rules into the stored decision before they create or update the app session that would own them, and every error exit in between leaves the work half done. On the create path, `postAppSessCtxProcedure` (`policyauthorization.go:163`) deduplicates the requested rule by `afAppId` (`:255`), creates it (`:257`) and writes it into the decision via `util.SetPccRuleRelatedData` (`:270`); the owning id is registered into `appSession.RelatedPccRuleIds` only at `:401`, on the success path. On the modify path, `HandleModAppSessionContext` (`:544`) installs each new-flow rule through `handleMediaSubComponent` (`:122`, direct write at `:659`) and writes the ids back to `appSession.RelatedPccRuleIds` only at `:804-806`, again on the success path.

Between installation and ownership sit five error exits — one defect pattern with five doors. On create: `:366` ("Sponsored Connectivity not supported"), `:375` (`extractUmData` fails, "usageThreshold is nil in USAGE REPORT Subscription"), and `:384` (return after `handleSponsoredConnectivityInformation` rejects with "usage Monitor Control is not supported in SMF"). On modify: `:785` (`extractUmData`) and `:797` (sponsored connectivity / usage monitoring). Issues #1181, #1184 and #1185 document `:384`, `:375` and `:785` respectively; `:366` and `:797` are unreported but share the defect, and `:366` is in fact the door a stock deployment hits — free5gc's own SMF negotiates suppFeat `000f`, which leaves bit 12 (SponsoredConnectivity) clear, so the gate at `:364-366` fails after the rule was already written. The three reported exits require a peer that negotiated bit 12, which our investigation harness produced by creating SM policies with suppFeat `0800` or `0fff`. Any fix scoped to one check would therefore leave the others open; the fix below guards the handlers, not the exits.

Once a request exits through any of these doors, the rule is unreleasable: no app session references it, so the delete path can never reach it, and the only remaining release is the deletion of the whole SM policy at PDU-session teardown (`internal/sbi/processor/smpolicy.go:516`). Growth is bounded only by the attacker's patience: because `GetPccRuleByAfAppId` (`internal/util/pcc_rule.go:147`) deduplicates on `afAppId`, each rejected request carrying a fresh `afAppId` adds exactly one rule plus its QosData entry (and, on the modify path, TrafficControlData), with no cap anywhere in the request path.

## Measured impact

On the stock `free5gc/pcf:v4.3.0` image the leak is deterministic and linear: 30 rejected creates left exactly 30 orphaned rules (slope 1, HTTP 403 `REQUESTED_SERVICE_NOT_AUTHORIZED` on every request), while the control with a fixed `afAppId` stayed at 1 rule because of the dedup. The orphaned rules are not inert: `smPolicy.PolicyDecision` is what the handler sends to the SMF on the next successful app-session update (`:442` create, `:847` modify). Measured on the same image, after the injected rejects one accepted create made the SMF log `In HandleSMPolicyUpdateNotify` followed by `apply sm policy decision error: too few fields 0` — the SMF does receive the rejected rules inside the victim's decision, although this SMF build refuses to apply them, so no downstream programming was observed and we claim none. Scaling the same attack to roughly 13,600 rejected creates in about 90 seconds grew the PCF process by about 21 MB before an unrelated concurrency defect killed the process (see Known limitations); memory exhaustion by this leak alone is therefore slow, while the unbounded rule growth inside the decision is the primary, immediately demonstrable effect.

## Fix process

The fix lives entirely in one file, `internal/sbi/processor/policyauthorization.go`, and changes neither the API surface nor any model or context type. Both handlers — `postAppSessCtxProcedure` and `HandleModAppSessionContext` — take, immediately after the SM policy is bound, a rollback guard: a `defer` that runs unless a `committed` flag was set just before the success return. Any rejection between installation and commit releases what that request added, so a 403 leaves the stored decision exactly as it found it, on all five exits at once.

The first revision derived the release set from a snapshot: on entry it recorded the rule-id set, the length of `PolicyCtrlReqTriggers` and both id generators, and on rollback it deleted every rule present in the live decision but not in the snapshot, truncated the triggers and rewound the generators. It passed the A/B verification, but it is unsafe when two requests touch the same SM policy concurrently: a diff taken against a snapshot can delete a rule that another in-flight request has just legitimately installed, and rewinding the id generators can hand out an id that a live rule already carries. The current revision removes that hazard at the source. Every site that installs a *new* rule — the two inline creation sites in the create handler and the new-rule branch of `handleMediaSubComponent`, which gained one out-parameter — appends the id to a request-local `createdRuleIds` list. The rollback releases exactly that list through the same `smPolicy.RemovePccRule` path the normal app-session delete uses, so associated QoS/traffic-control/charging/usage-monitoring data is removed with the rule and ownership is reconciled against the app-session pool before anything is deleted; nothing that a live app session owns can be caught by the rollback. Trigger truncation is kept, and the generator rewind of the first revision is retained deliberately.

Against pristine v1.4.6 the fix is +98/−3 lines in the single file; the resulting `fix.patch` (183 lines) applies cleanly to an unmodified checkout, and `go build`, `go vet`, `go test ./...` and `gofmt` are clean on v1.4.6.

## Validation

Verification was end-to-end on the compose deployment rather than unit-only. Against the stock image, the bundle's PoC showed 50 rejected creates producing 50 retained rules (verdict EXPLOITABLE); against the fixed build the same 50 requests still received 403 but retained 0 rules (verdict NOT REPRODUCED), with the PCF logging one `Roll back PCC rule[...]` line per rejected request. The fixed PCF was then deployed as the live stack's PCF and exercised by real registration traffic: both simulated UEs registered and attached, the PCF served the AM-policy create and both SM-policy creates with HTTP 201, and the data plane passed — `ping` through `uesimtun0` (10.60.0.22) and `uesimtun1` (10.61.0.22) reached the UPF with 0% loss at about 2.2 ms and the internet with 0% loss at about 210 ms. The validated build is published as `swr.cn-north-4.myhuaweicloud.com/cn_5gc/pcf:v4.3.0-pccfix` (digest `sha256:83cc3ac16adcf3bd1e2d65af920bffde57ffca8372224217cc2c1a48e7a9f206`).

## Known limitations

The fix addresses the leak demonstrated by the three issues and does not pretend to more. It adds no locking: concurrent app-session requests against the same SM policy remain unsynchronised, and under heavy load the stock build can die on a `concurrent map iteration and map write` fatal error while a reader JSON-encodes the decision a writer is mutating — a separate CWE-362 defect that this patch does not close (it adds two bounded traversals per rejected request, which marginally widens that window). The dedup branch of `handleMediaSubComponent` mutates an existing rule's QoS in place and consumes the session's GBR budget scalars; a later rejection of such a modify therefore still leaves the mutated QoS and a reduced budget behind, and that behaviour is out of scope here. Finally, the rollback snapshot captures the trigger list and two id generators but not the charging-id generator.

## Reproducing with the bundle's PoC

Run the script against a stock deployment, naming the victim SM policy: `python3 pcf_pcc_rule_leak_exploit.py --policy imsi-208930000000001-1 --requests 50` (the PCF defaults to `http://10.100.200.7:8000`; override with `--pcf`). The script reads the victim's decision through the PCF's own `GET /npcf-smpolicycontrol/v1/sm-policies/{id}` endpoint for a baseline, sends the configured number of sponsored app-session creates with a fresh `afAppId` each, reads the decision again, and prints the delta. On the stock build every create returns 403 and the count rises by exactly N (verdict EXPLOITABLE); on the fixed build the creates still return 403 but the count is unchanged (verdict NOT REPRODUCED), and `docker logs pcf 2>&1 | grep -c "Roll back PCC rule"` shows one rollback line per request.
